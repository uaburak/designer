1. What Figma's player does with a spring (viewer bundle)
---------------------------------------------------------
- s1.easingFunctionValues(): for CUSTOM_CUBIC, GENTLE_SPRING, SPRING_PRESET_ONE/TWO/THREE and CUSTOM_SPRING the
  action's own easingFunction when it has one, else the preset's numbers (legacy SPRING and the beziers: the preset).
- s1.transitionDuration(): the stored transitionDuration (≥ 0), else 0.3.
- s$.getYValueForXValue(x) = spring.solve(x · durationSeconds): the physical spring runs in real seconds over the
  stored duration.
- sX (the spring): ω₀ = √(k/m), ζ = c / (2√(km)); ζ < 1 the under-damped closed form; ζ ≥ 1 the critically damped
  curve at ω₀: 1 − (1 + (ω₀ − v₀)t)·e^(−ω₀t) (Slow, ζ ≈ 1.118, plays as critical).
So the owner's card hover lasts 0.417 s and moves 1 − (1 + 26.8t)e^(−26.8t); a Push 0.625 s.

Wecra before: `proto::durationOf` ignored the stored duration for every spring and played the preset's own settle
time, and `springOf` ignored easingFunction for presets — every Slow animation of the file ran Slow's own 1.25 s:
3× (cards), 4.8× (buttons) and 2× (navigation) longer than Figma, with the over-damped curve (slower start). That is
the "very heavy" playback: frame pacing was never the problem (below).

3. Layout grids in the presentation
-----------------------------------
Frames 1–6 carry a 12-column layout grid. Figma never draws layout grids in the preview or the presentation; Wecra drew
them over every screen (red / blue columns, seen in the Present tab's capture). Fixed: renderScene draws no layout
guides.

4. Play with a section / a frame in it
--------------------------------------
Figma: the section "Desktop" selected, ⇧Space → the inline preview at frame "1", one frame as the screen (its own
viewport, not the section). A frame in the section selected → that frame. Nothing selected → the first flow ("1").
Wecra before: the toolbar's Play / ⇧Space / Present in this tab with the section selected sent no start node (the
editor's presentStart answers undefined for a section) and the player started at the page's first flow — "1" here
only because Flow 1 is inside the section; a section without a flow inside it started wherever the page's first flow
or first frame is, maybe outside the section. Now (ours, inferred from the live case: Flow 1 is both the section's first
flow and its first child and top-left): a section selected (or a layer only sections hold) starts at the first flow
starting inside it, else its first frame in layer order (proto::sectionStart) — always one frame. Checked live in Wecra
on the owner's file: ⇧Space, Present in this tab and the toolbar's Play (the Present tab) with the section → "1"; with
frame 4 → "4"; with a layer in frame 2 → "2"; nothing → "1".
Not reproduced: "it plays every frame of the section" — in the built app every entry point showed one frame. What did
show many columns over every screen was the layout grid (§3), which looks like the frames' strips.
